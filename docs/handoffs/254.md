## 契約と互換性

| 要求 | API / 結果 |
| --- | --- |
| 保存済み動的 name | 同じ queue の名前一致 → `handle(..., { defaultForQueue: true })`。保存値を変更しない |
| typed result | `defineJob<TPayload, TResult = void>`。BullMQ `returnvalue` へ返す。enqueue は ID/name のまま |
| readiness | `runtime.ready(queues?, { timeout }?)`。Worker を作らない |
| producer-only 解放 | start なしでも `stop()` で管理 Queue を閉じる |
| 障害通知 | manager 第2引数 `onError`。接続終了・予期しない run 終了を利用側が判断 |
| 停止 | Worker drain → Queue close。全 settlement、集約失敗、期限後も cleanup 継続 |

TypeScript >=5.4、BullMQ `^5.16.0 || ^6.3.11`。両 package に major Changeset。
既存 void / constructor 第1引数 / pause・resume は維持するが、起動後の登録、重複 default、
停止中の新規操作は拒否し、producer stop は実際に解放する。cleanup 失敗後は新 manager が必要。
借用 client は呼出側が所有する。型は既存 Redis payload の validation を代替しない。
options 経路には ioredis 5.x を明示導入する（adapter は `^5.0.0` optional peer）。
BullMQ 6 の optional ioredis peer は自動導入されない。借用 client の driver は利用側が管理する。

## 成果物の作成と取得

```bash
pnpm pack:prep /path/outside-checkout/empty-artifacts --require-clean
pnpm verify:packed /path/outside-checkout/empty-artifacts
```

pack は必ず fresh build し、staging の版だけを `0.0.0-prep.g<FULL_SHA>` にする。
dirty preview には `.dirty.<SOURCE_FINGERPRINT>` を追加し、同じ commit の変更内容を区別する。
tracked / nonignored untracked 全入力と両 package の src（ignore 対象も含む）の名前・mode・bytes の hash を前後で比較し、manifest に残す。
source symlink は拒否し、依存 snapshot は作らない。build 出力は checkout 外だけに生成する。
adapter の core 依存は同じ exact version。tracked `0.1.0` は変更しない。
ローカル dirty 実行は manifest に明記され、採用用の clean-source 証拠にはならない。
consumer は workspace 外で両 tarball だけから library を導入する。BullMQ 5.16.0 / 6.3.11 と
TypeScript 5.4.5 / ioredis 5.11.1 を各 consumer に明示導入し、strict peers / skipLibCheck:false で検証する。
Redis は adapter devDependency の TestContainers（redis:7.4.2-alpine）を自身で起動・終了する。
明示的な専用テスト Redis のみ `PACK_TEST_REDIS_URL` で指定可能。利用者インフラは使わない。
内部 helper は Linux の専用 process group を終了し、直接子の close と実行可能な子孫の
終了を待ってから一時 consumer / staging / logs を削除する。3分の command deadline と
終了 code を検査する。daemon 化・setsid は対象外。supervision 自体が失敗した場合は
プロセスを異常終了して一時ファイルを保持する。command の失敗を上位へ返す。

CI は最初に source commit を一度解決し、すべての job を同じ SHA へ固定します。
`packed-consumer` job は matrix / test / lint 成功後に実行し、tarballs、manifest、
consumer-receipt を **30日**保持する。失敗時も診断 artifact を上げるため、workflow/job と
manifest / receipt の成功をすべて確認して採用する。npm publish は行わない。
artifact 名は `mokuroku-prep-<FULL_SHA>-<RUN_ID>-<ATTEMPT>`。

```bash
# 実際の run / SHA / attempt を台帳から入力する
REPO=mokuroku-community/mokuroku-js
RUN_ID='<run-id>'
SHA='<full-checked-out-commit>'
ATTEMPT='<run-attempt>'
gh run view "$RUN_ID" --repo "$REPO"
gh run download "$RUN_ID" --repo "$REPO" \
  --name "mokuroku-prep-$SHA-$RUN_ID-$ATTEMPT" --dir ./mokuroku-prep
node --input-type=module - ./mokuroku-prep "$SHA" <<'NODE'
import assert from 'node:assert/strict';
import { readFileSync } from 'node:fs';
import { createHash } from 'node:crypto';
const [dir, sha] = process.argv.slice(2);
const manifest = JSON.parse(readFileSync(`${dir}/manifest.json`));
assert.equal(manifest.source.sha, sha);
assert.equal(manifest.source.dirty, false);
assert.equal(manifest.status, 'packed');
assert.equal(JSON.parse(readFileSync(`${dir}/consumer-receipt.json`)).status, 'passed');
for (const p of manifest.packages) {
  assert.equal(p.integrity, 'sha512-' + createHash('sha512').update(readFileSync(`${dir}/${p.file}`)).digest('base64'));
}
NODE
```

期限切れは同じ commit を clean checkout し、Node 24 / pnpm 10.34.5 で CI を再実行する。
新 run / attempt / integrity を記録し、古い取得先の成功を推定しない。

#255 consumer は tarballs を `vendor/core.tgz` / `vendor/adapter.tgz` に置き、次を設定する。

```json
{
  "dependencies": {
    "@mokurokujs/core": "file:./vendor/core.tgz",
    "@mokurokujs/bullmq-adapter": "file:./vendor/adapter.tgz",
    "bullmq": "6.3.11",
    "ioredis": "5.11.1"
  },
  "pnpm": { "overrides": { "@mokurokujs/core": "file:./vendor/core.tgz" } }
}
```

`pnpm install --strict-peer-dependencies` を使い、peer 無視や workspace source alias は使わない。
検証 script は ESM root import、公開 d.ts の正負 payload/result、root/adapter から解決した
core の realpath / version 一致、raw 保存 dynamic name → typed returnvalue → ready/stop、
producer Worker 数0を確認する。manifest には pack 時の tool versions、consumer receipt には
固定 TS / BullMQ と root / BullMQ 両方から実解決した ioredis / Redis 版・実行 command / 結果が残る。

## #255 の残責任

| queue | 維持する挙動 |
| --- | --- |
| `endedPollNotification` | Note ID name / payload / delay、自動 jobId、attempts 未指定、void、既定 concurrency |
| `deliver` | 既存 name 変換と snapshot、既定12試行、custom backoff、concurrency / 秒間128、文字列結果、非再試行変換 |
| `userWebhookDeliver` | webhook snapshot、4試行、concurrency / 秒間64、文字列結果、status 更新 drain |

全3 queue で成功保持 `{ age: 604800, count: 30 }`、失敗保持 `{ age: 604800, count: 100 }`、
prefix、metrics 1週間を consumer 設定に残す。根拠は
[固定済み利用側 tree](https://github.com/tiramiss-community/tiramiss/tree/d83306eccdb654d1524b272970200dd9787f69c0/packages/backend-next/src/platform/job-queue)。

1. producer / worker manager を分離。HTTP は ready / enqueue / stop のみ使う。
2. 各 queue の型付き定義と default handler を登録し、業務へ `deliverMany` 等の具体的能力を渡す。
3. 保存ジョブを変換・clear せず消費。実経路へ接続してから旧 wrapper / 登録 / 不要 assembly を撤去。
4. 現行の無再接続設定と failure 通知を接続する。
5. Worker stop → handler 後続 drain → producer / 共有接続解放の順序を維持する。
6. 既存 handoff / retry / 保持 / 管理 API / QueueStats 比較を再利用し、Supervisor / 停止期限 / 異常終了を実プロセスで検証。
7. 採用 commit / artifact / 旧新経路 / 実測 / 未移行箇所 / 担当 / 再評価条件を記録。

未対応7 queue、system 9 scheduler、最終切替 #139 は既存担当に残す。
本 handoff は準備であり、利用側移行・merge・version 適用・release・publish を完了したとは扱わない。
